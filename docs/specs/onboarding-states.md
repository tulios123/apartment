# אפיון — אשף-קליטה מודע-מצב

**סטטוס:** טיוטה לאישור הבעלים · נכתב 06.09.2026
**מקור הבקשה:** "הדבר הכי משמעותי זה אשף הקליטה. שיפוץ משמעותי, ושיחזיק מצבים שונים.
הדקה הראשונה באפליקציה זו הנקודה החשובה ביותר. יש חבר ואח שלי שנכנסו לאפליקציה
אבל עוד לפני העברת המפתח."

מסמך זה מאפיין **את המצבים ואת מה שהם משנים** — לא את העיצוב. העיצוב יתוכנן אחרי
שהבעלים יאסוף רפרנסים.

## 1. הבעיה, עם ראיות

### 1.1 האשף מניח מצב אחד
`src/components/onboarding/types.ts:7` מגדיר סדר קבוע:

```ts
export const STEP_ORDER: Step[] = ['purchase', 'mortgage', 'loans', 'investment', 'rental', 'insurance']
```

הקבוע הזה הוא מקור-האמת גם לנקודות-ההתקדמות (`StepDots.tsx`) וגם לשורה
"שלב N מתוך M" (`StepHeader.tsx`). הוא זהה לכל אדם, ולכן **כל משתמש רואה שישה
שלבים**, גם כשארבעה מהם מדברים על משהו שלא קיים אצלו.

מסך-הפתיחה (`WelcomeStep.tsx:9-14`) מבטיח ארבעה נושאים, שהאחרון בהם:

```ts
{ Icon: Key, label: 'הכנסות', sub: 'שכירות, תזכורות וביטוח' }
```

ומסך-הסיום (`DoneStep.tsx:36`) חוגג "הנכס שלך מוגדר — אפשר להתחיל לנהל."

כלומר ההנחה "יש לך דירה מושכרת" מוטבעת מהמסך הראשון עד האחרון.

### 1.2 הנזק האמיתי הוא אחרי האשף
האשף אינו מסך — הוא קובע איך האפליקציה מתנהגת בחודשים שאחריו. שלוש נקודות:

**(א) התראת-פוש שאי אפשר לפעול לפיה.**
`supabase/functions/daily-reminders/index.ts:179-186`:

```ts
if ((liveContracts ?? []).length === 0) {
  const { count } = await supabase.from('properties')...
  if ((count ?? 0) > 0 && cadenceDue('no-lease', NO_LEASE_REPEAT_DAYS)) {
    lines.push('אין חוזה שכירות פעיל — מומלץ להוסיף שוכר חדש')
```

`NO_LEASE_REPEAT_DAYS = 14`. מי שיש לו נכס ואין חוזה פעיל מקבל את ההודעה הזו
**כל שבועיים**. עבור רוכש שהמסירה שלו בעוד שמונה חודשים: כ-17 התראות שממליצות
להכניס דייר לדירה שאי אפשר להיכנס אליה. זה הבאג הקונקרטי שהאח והחבר חווים.

**(ב) מסך-הבית מציג "חוסר" קבוע.**
`src/pages/dashboard/HomeScreen.tsx:501-508` — כשאין חוזה פעיל:

> **אין חוזה שכירות פעיל** · הוסיפו שוכר כדי לעקוב אחרי ההכנסה החודשית

זה נכון למי שמחפש דייר, ולא נכון למי שממתין למפתח. עבורו זו הודעת-כישלון
קבועה שתלווה אותו חודשים, על משהו שהוא לא יכול לתקן.

**(ג) מסכי-הכסף מציגים אפס במקום "טרם התחיל".**
`HomeScreen.tsx:567-569` — "הצפי כולל רק את ההוצאות הקבועות. הוסיפו חוזה שכירות
כדי לראות גם את ההכנסה." · `WealthHub.tsx:52-53` — כל התשואות נגזרות מ-`monthlyRent`,
שהוא 0. תשואה 0% היא אמירה שגויה על ההשקעה; הנכון הוא "טרם החלה הכנסה".

### 1.3 מה כבר עובד נכון (ולא לגעת)
- `emptyTrack(keyDeliveryDate)` — מסלולי-משכנתא מתחילים כברירת-מחדל בתאריך-המסירה
  (`PurchaseStep.tsx:38`), ולכן התחזית **לא** מחייבת תשלומי-משכנתא לפני הזמן.
- `dueDayOfMonth` בפילטר של `daily-reminders` — תזכורת שכ״ד לא רצה בלי חוזה חי.
- `liveContractIds` — פריטים חוזרים של חוזה שנגמר לא מנדנדים.

זאת אומרת: **מנוע-הכסף כבר מודע-זמן. מה שלא מודע-מצב הוא הניסוח והניווט.**

## 2. המודל — שתי עובדות, שאלה אחת

הפיתוי הוא להגדיר "מצב" כאחד מארבעה. זה שביר: מי שקנה, טרם קיבל מפתח, וכבר חתם
חוזה שכירות שמתחיל ביום המסירה — נמצא בשני מצבים בו-זמנית, וזה מצב לגיטימי ונפוץ.

לכן המערכת מחזיקה **שתי עובדות בלתי-תלויות**, והמשתמש עונה על **שאלה אחת**.

### 2.1 עובדה א׳ — האם הדירה ברשותי?
```
טרם-מסירה  ⇔  property.key_delivery_date קיים  וגם  גדול מהיום
ברשותי     ⇔  כל מקרה אחר (תאריך ריק, או תאריך שעבר)
```

התכונה החשובה: **המעבר קורה מעצמו.** ביום שהתאריך עובר, המצב מתהפך בלי שאף אחד
יעשה דבר ובלי מנגנון-מעבר. אין שדה חדש, אין מיגרציה.

הכיוון של הכלל נבחר בכוונה: ברירת-המחדל היא "ברשותי". רק מי שמילא במפורש תאריך-מסירה
עתידי נכנס למצב טרם-מסירה. משמעות מעשית: **אף משתמש קיים לא משנה התנהגות** — כולם
נשארים בדיוק איפה שהם.

### 2.2 עובדה ב׳ — מה מצב השכירות?
נגזר מ-`activeContract()` (`src/lib/projections.ts:39-48`) ומרשימת החוזים:

| מצב | הגדרה |
|---|---|
| `leased` | קיים חוזה ש-`start_date ≤ היום ≤ end_date` |
| `signed` | אין חוזה פעיל, אך קיים חוזה עם `start_date` עתידי |
| `searching` | אין חוזה פעיל ולא עתידי, **והיה** חוזה בעבר |
| `none` | מעולם לא היה חוזה |

`signed` ו-`searching` אינם קיימים היום — הקוד מכיר רק "יש חוזה פעיל / אין".
שניהם נגזרים מנתונים שכבר יש, בלי שדה חדש.

### 2.3 הצמד → מה המשתמש רואה
| ברשותי? | שכירות | מה זה בפועל | האפליקציה |
|---|---|---|---|
| טרם | `none` | קניתי, ממתין למפתח | ספירה למסירה; שכירות מושתקת |
| טרם | `signed` | קניתי, כבר יש דייר לכניסה | ספירה למסירה **וגם** הדייר הממתין |
| כן | `leased` | מושכרת — **מצב כל המשתמשים היום** | בדיוק כמו היום, אפס שינוי |
| כן | `none`/`searching` | הדירה בידיי, מחפש דייר | הזמנה להוסיף שוכר (כמו היום) |

## 3. מה כל מצב משנה

### 3.1 מסלול האשף
```
מושכרת / מחפש דייר   רכישה ← משכנתא ← הלוואות ← השקעה ← שכירות ← ביטוח   (6)
טרם-מסירה             רכישה ← משכנתא ← הלוואות ← השקעה ← ביטוח           (5)
```
שלב-השכירות יורד רק במצב טרם-מסירה. הנקודות ו"שלב N מתוך M" נגזרות מהמסלול בפועל
במקום מהקבוע `STEP_ORDER` — כך שהמספר אומר אמת.

**שלב הביטוח נשאר** גם לפני מסירה: ביטוח-מבנה וביטוח-חיים למשכנתא נדרשים בדרך-כלל
כתנאי לביצוע ההלוואה, לפני המסירה. הניסוח מותאם: "מתחיל בדרך כלל במסירת המפתח",
ותאריך-ההתחלה בטופס כבר ממילא ברירת-מחדל לתאריך-המסירה (`PolicyForm.tsx:85`).

### 3.2 התראות (`daily-reminders`)
| התראה | טרם-מסירה | ברשותי |
|---|---|---|
| `no-lease` (כל 14 יום) | **מושתקת** | כמו היום |
| שכר-דירה / אישור-קבלה | לא רלוונטית (אין חוזה חי) | כמו היום |
| חידוש-חוזה | כמו היום | כמו היום |
| משימות | כמו היום | כמו היום |

השינוי בקוד הוא תנאי אחד: לפני `cadenceDue('no-lease', …)` לבדוק שאין
`key_delivery_date` עתידי. הפונקציה כבר שולפת `properties` בשביל ה-`count`.

**זה תיקון שאפשר לשחרר מיד, בנפרד מכל השאר** — ראו §6.

### 3.3 מסך-הבית
במצב טרם-מסירה, במקום כרטיס "אין חוזה שכירות פעיל":
- ספירה למסירת-המפתח (התאריך והמרחק ממנו)
- מה שכן קורה בינתיים: תשלומי-משכנתא שהחלו, ביטוח, משימות פתוחות
- ניסוח-הצפי משתנה ל"הכנסה תתחיל אחרי מסירת המפתח" במקום "הוסיפו חוזה שכירות"

**התוכן המדויק של המסך הזה הוא ההחלטה הפתוחה המרכזית** — ראו §5.

במצב `signed` (חוזה חתום שטרם התחיל) — גם היום המסך מציג "אין חוזה שכירות פעיל",
שזו אמירה לא-מדויקת: יש חוזה, הוא פשוט טרם התחיל. הנכון: "הדייר נכנס ב-X".

### 3.4 מסכי-ההון והתשואה
כש-`monthlyRent = 0` מסיבה לגיטימית (טרם-מסירה), תשואה מחושבת היא 0% — מספר שגוי.
במצב זה יוצג "טרם החלה הכנסה" במקום ערך. אין שינוי בחישוב עצמו, רק בשער-התצוגה.

### 3.5 המעברים
| מעבר | מתי | מנגנון |
|---|---|---|
| טרם-מסירה → ברשותי | התאריך עובר | **אוטומטי.** אין קוד-מעבר |
| ברשותי → מושכרת | נוסף חוזה | קיים היום |
| מושכרת → מחפש דייר | החוזה נגמר | קיים היום |

הדבר היחיד שדורש קוד הוא **הרגע**: ביום שהמפתח נמסר, האפליקציה מברכת פעם אחת
("המפתח שלך") ומציעה את הצעד הבא. בלי זה המעבר יקרה בשקט והמשתמש לא ישים לב
שמסך-הבית שלו השתנה.

## 4. מסך-הבחירה

שאלה אחת, אחרי מסך-הפתיחה ולפני שלב-הרכישה. שלושה כרטיסים.

עיקרון-הניסוח (בקשת הבעלים — "שהמידע שם יהיה מדויק"): **כל כרטיס אומר גם מה
המצב וגם מה יקרה בעקבותיו.** ברגע שבחירה משנה התנהגות, ניסוח מעורפל גורם לאדם
לבחור לא-נכון ולגלות זאת חודש אחר-כך.

טיוטת-תוכן (לא עיצוב):

1. **הדירה מושכרת**
   יש שוכר בפנים, או חוזה חתום שמתחיל בקרוב.
   → נגדיר גם את השכירות והתזכורות · 6 שלבים

2. **קניתי — המפתח עוד לא אצלי**
   חוזה הרכישה חתום, המסירה עוד לפנינו.
   → נדלג על השכירות ונחזור אליה כשהמפתח יימסר · 5 שלבים

3. **המפתח אצלי — עדיין אין שוכר**
   הדירה בידיים שלי, מחפשים דייר.
   → נגדיר את הנכס והמימון; השכירות תחכה · 6 שלבים

בתחתית: "אפשר לשנות בכל שלב" — ואמירה זו חייבת להיות נכונה, כלומר חייבת להיות
דרך גלויה לשנות אחר-כך (מסך הנכס).

**מה הבחירה עושה טכנית:** היא אינה נשמרת כשדה. בחירה 2 פשוט הופכת את
תאריך-המסירה לשדה-חובה בשלב-הרכישה; משם המצב נגזר מהתאריך לנצח. בחירות 1 ו-3
נבדלות רק בהדגשה של שלב-השכירות. כלומר **הבחירה מכוונת את האשף, והנתונים
מחזיקים את האמת.**

## 5. החלטות פתוחות — לבעלים

1. **מצב רביעי, "גר בדירה בעצמי"** — בפנים או בחוץ? הוא אינו ניתן לגזירה מאף
   נתון קיים, והוא משנה את כל האפליקציה (אין הכנסה, אין תשואה, המשכנתא היא הוצאה
   אישית ולא עסקית). **המלצה: בחוץ.** האפליקציה היא לניהול השקעה.

2. **מסך-הבית לפני מסירה — מה הוא מציג?** זו ההחלטה שקובעת אם המצב הזה שווה
   משהו או שהוא רק "בלי נדנוד". אפשרויות: ספירה יבשה למסירה · רשימת-הכנות
   (ביטוח, פתיחת חשבון, בדיקת ליקויים, חיפוש דייר) · או תמונת-ההשקעה עד כה
   (כמה הון הוכנס, מה החוב). **צריך את הרפרנסים כדי להחליט.**

3. **שאלה או גזירה?** האם להציג מסך-בחירה מפורש (§4), או פשוט לשאול "מתי נמסר
   המפתח?" בשלב-הרכישה ולגזור הכול משם — בלי מסך נוסף. **המלצה: מסך מפורש** —
   הוא מה שביקשת, והוא גם היחיד שמאפשר להסביר את ההשלכה מראש.

4. **משתמשים קיימים** — לפי §2.1 אף אחד מהם לא מושפע (כולם "ברשותי"), ואין
   אונבורדינג מחדש. מאשר?

## 7. מה המסמך הזה לא מכסה
- עיצוב: פריסה, צבע, איורים, אנימציה. מחכה לרפרנסים.
- שכבה שלישית של השיפוץ (מסמך-קודם-כול כמסלול מהיר, פחות שדות במסך, שמירה
  מתקדמת) — הוגדרה בשיחה אך לא אופיינה כאן; היא בלתי-תלויה במצבים.
- מצב "בתהליך קנייה, טרם חתמתי" — לא נכלל; אין מה לשמור לפני חוזה.
